# docs-sync

## これは何のためのスキルか

このリポジトリ(dotfiles)は「本格的な設計書は作らない」方針を取っており、方針は
`CLAUDE.md`、利用者向けの説明は `README.md`、未決定の検討事項は `TODO.md`、複数の
選択肢から何かを選んだ理由は `docs/decisions/*.md`(ADR)に分散して書かれている
(詳細は `CLAUDE.md` の「ドキュメント」節参照)。

ドキュメントが複数箇所に分かれている構成は、実装を変更したときに「一部だけ更新して
残りが古いまま取り残される」劣化が起きやすい。実際にこのリポジトリで起きた例:

- `nix/` で home-manager 導入を進めた際、README には「nix-installer のアンインストール
  は綺麗」という記述だけが足され、日常運用でのパッケージ・世代のガベージコレクション
  (`nix-collect-garbage` 等)については何も書かれず、実際そのコマンドもリポジトリの
  どこにも存在しない状態になっていた。
- bash 側にも zsh と同様の汚染対策(ブートストラップ方式)を追加したあとも、
  `docs/decisions/zshrc-pollution.md` のトレードオフ節が旧方式(境界コメントのみ)
  時代の記述のまま更新されておらず、`install.sh` の実装(`bootstrap_file()` の実際の
  挙動)と食い違っていた。

このスキルは、実装変更のあとに「書いてあること」と「コードの実際の挙動」を突き合わせ、
ズレを見つけて直す。package-researcher スキル(`.claude/skills/package-researcher/`)
が実践している「書いてある(公式ドキュメントに記載がある)≠推奨されている」という
教訓と同じ精神で、ここでは「書いてある(READMEやADRにそう書いてある)≠実態と一致
している」を毎回確認する。読んだだけで安心せず、必ずコードを読む・grep する・
実際に試すところまでやること。

## いつ使うか

- ユーザーから明示的に依頼されたとき。
- 実装系タスク(新しいコマンド・関数・オプションの追加、`home/`・`nix/`
  の構成変更、`update.sh`/`scripts/` の挙動変更)を完了した直後。
  `verify` スキル(実際に動くかどうかの確認)とセットで使うことが多いが役割は別:
  `verify` は「動くか」、`docs-sync` は「書いてあることと動きが一致しているか」を見る。
- ドキュメントのみの修正(誤字・リンク切れ)、比較対象となる実装変更が存在しない
  ADR の新規追加だけのときは使わなくてよい。

## 進め方

### 1. 今回の変更点を特定する

`git diff` / `git log` を見て、実装が何を変えたか(新しいコマンド名、削除/追加した
オプション、挙動の変化点)を把握する。セッション内で既に変更内容を把握している場合は
このステップは省略してよい。

### 2. 影響範囲のドキュメントを洗い出す(質問の範囲に閉じない)

変更点に関連する記述を `README.md` / `CLAUDE.md` / `TODO.md` / `docs/decisions/*.md`
から探す(コマンド名・ファイルパス・キーワードで grep する)。

**ユーザーが特定の一点だけを聞いてきた場合でも、そこだけ答えて終わらせない。** 関連する
節・ファイル全体を通しで読み、他にもズレが無いか一緒に洗い出す。実際に、質問された一点
(掃除まわりのGC不足)だけに絞って調べた回では見つけられたのに、同じ README の Nix 節を
通しで読んだ回だけが見つけられたズレが2件あった: パッケージ一覧から `herdr` が抜けていた
ことと、`flake.lock` の生成手順コメントが実態(既にコミット済み)と食い違っていたこと。
どちらも質問した本人は気づいていなかった類のズレであり、「聞かれたことだけに答える」
姿勢では拾えない。ユーザーは「変更をしたときは関連ドキュメント全体を直してほしい」と
明確に求めているので、質問・変更の直接の対象だけでなく、その変更が触れている
セクション・ファイル全体を対象に含めること。

次の3種のズレを特に意識する:

- **a. 存在しない対象への言及**: 書かれているコマンド・オプション・ファイルパスが
  実際には存在しない、または名前が変わっている(`command -v` や `grep` で確認できる)。
- **b. 主張と実装の不一致**: 「〇〇できる」「〇〇される」という記述に対し、実装を
  読むと実際にはそうなっていない、または一部しか実現していない(例: 「アンインス
  トールが綺麗」は Nix 本体の話であって、日常のパッケージ GC には触れていない、
  といった主張のスコープのすり替わりも含む)。
- **c. 実装は変わったが記述が古いまま**: 特に ADR のトレードオフ節・履歴節、
  `CLAUDE.md` の方針要約は、機能追加時に本文だけ直して更新し忘れやすい。

### 3. 見つけたズレを断定せず提示する

「〇〇だと思われる」「読んだ範囲ではこう見える」という確度で、具体的に
`ファイル:行番号` 付きで一覧にしてユーザーに提示する。見つけたら黙って直さない。
この作業スタイルはこのリポジトリで既に確認済みの進め方(ドキュメント修正のような
軽微な変更でも、直すかどうかを毎回ユーザーに選ばせる)を踏襲する。一覧は次の形式で:

| ファイル:行 | 現在の記述 | 実装が示す実態 | 提案 |
|---|---|---|---|
| README.md:51 | 「アンインストールが綺麗」 | `nix-collect-garbage` の類は未実装・未記載 | GC コマンドの案内を追記する/しない |

### 4. 承認された項目だけ直す

ユーザーが直すと言った項目だけ編集する。`docs/decisions/*.md`(ADR)を編集する際は
`docs/decisions/README.md` の規約を必ず守る:

- 過去の記録は書き換えない。**決定そのものを覆す**場合のみ末尾の「履歴」節に時系列で
  追記する(本文の全面書き換えはしない)。
- 一方、"記述の古さを実態に合わせて直す"(決定は変わっていないが、トレードオフ節が
  古いままだった、等)は本文の該当箇所を直接編集してよい。決定そのものを覆す変更なのか、
  単なる記述の追いつきなのかを、編集前に必ず見極めること。
- ファイル名・構成(検討した代替/選んだ理由/トレードオフ)などその他の規約は
  `docs/decisions/README.md` 参照。

## 参考

- `.claude/skills/package-researcher/`: 「書いてある≠推奨」を一次情報で確認してから
  実装するという進め方の参考。ここでの「書いてある≠実態」の確認姿勢と同じ精神。
- `verify` スキル: コード変更が実際に動くかどうかの確認。役割が異なるため混同しない。
