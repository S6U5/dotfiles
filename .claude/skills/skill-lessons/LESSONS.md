# スキル作成・改善の教訓集

`.claude/skills/` 配下のスキルを skill-creator で作成・評価・改善する中で判明した、
AI が陥りがちな間違いやスキルの書き方・評価の仕方の教訓を集約する。書き方・運用ルールは
`.claude/skills/skill-lessons/SKILL.md` 参照。

過去のエントリ本文は基本的に書き換えない(追記のみ)。

## 2026-08-01 — eval-methodology: skill-creator の `run_loop.py`/`run_eval.py`(トリガー最適化)は、実行時のカレントディレクトリを取り違えるとプロジェクトルートを誤認識し、スコアが常に低く出る

`run_loop.py` はスクリプト自身のディレクトリ(`cd $SKILL_CREATOR_DIR && python3 -m scripts.run_loop ...`)から実行したところ、内部の `find_project_root()` が cwd から上に辿って最初に見つかる `.claude` ディレクトリを「プロジェクトルート」とみなす実装のため、`$HOME/.claude`(グローバル設定ディレクトリ)を対象リポジトリと誤認識した。結果、`claude -p` が実際の dotfiles リポジトリ(README.md や install.sh がある場所)ではなく `$HOME` を cwd として起動され、should-trigger クエリ(「READMEに書いてあるけど本当?」等、リポジトリの実ファイルを前提とする質問)が軒並みトリガーせず、5イテレーション回してもスコアが全く改善しなかった(test 4/8 のまま)。**教訓**: このスクリプトは必ず対象リポジトリのルート(`.claude/` が直下にあるディレクトリ)を cwd にして実行する(`PYTHONPATH=<skill-creatorのパス> python3 -m scripts.run_loop ...` の形でモジュール解決だけ外部から行う)。cwd を変えて実行した場合は結果を信用せず、`find_project_root()` の戻り値を先に確認する。

## 2026-08-01 — eval-methodology: skill-creator のトリガー最適化(`run_eval.py`)は `.claude/commands/` に一時ファイルを作って擬似的に「スキル」を模擬するが、この方式ではプロジェクトスキル本来の自動発動(Skillツールの`available_skills`経由のトリガー)を正しく再現できず、実際にはよく発動する説明文でもスコアが恒常的に低く出た

上記の cwd 修正後(プロジェクトルートを正しく認識させた状態)でも、`run_loop.py` は5イテレーションとも同じ低スコア(test 4/8, train 6/12)から一切改善しなかった。原因を切り分けるため、実際の `.claude/skills/docs-sync` を使って `claude -p` を手動で複数回叩いたところ、同種の質問(例:「install.shのバグ直したから、READMEも直しておいて」)は問題なく `Skill` ツール経由で発動した。両者の違いは、`run_eval.py` が `.claude/skills/` ではなく `.claude/commands/` 配下に一時的な擬似スキルファイルを書き出して模擬している点にあり、この方式では実際の `available_skills` 自動トリガー機構を正確に再現できていないと考えられる。**教訓**: `.claude/skills/` 配下のプロジェクトスキル(SKILL.md 形式)については、`run_loop.py` のスコアを信用せず、実際の `claude -p <query>` を対象リポジトリ内で直接叩いて `Skill` ツール呼び出しの有無・引数を見る手動スポットチェックの方が信頼できる。少数(4〜6件)の should-trigger / should-not-trigger を手動で試すだけでも、自動ツールでは検出できない実在のギャップ(下記エントリ参照)が見つかった。

## 2026-08-01 — skill-writing: 「一見ただの単純な編集依頼」に見える should-trigger クエリは、description に具体的な言い回しの例が無いと発動しないことがある

docs-sync の手動スポットチェックで、「install.shに--verboseオプション追加したんだけど、READMEのオプション表も直しておいて」(実際には存在しないオプションの追記を装った依頼)が発動しなかった。一方、「install.shのバグ直したから、READMEも直しておいて」という類似の依頼は問題なく発動した。前者は「ただの単純な文書編集」に読める分、モデルが検証の必要性を認識しにくかったと考えられる。description に「〇〇にオプション/コマンドを追加したので、READMEの表を直しておいて」という具体的な言い回しを追加したところ、同じクエリで発動するようになった(修正後に再検証済み)。**教訓**: skill の description に既に例示フレーズがあっても、「単純な作業に見えるが実は検証が必要」なパターンは個別に具体例を挙げないと拾われないことがある。抽象的な言い回し(「実装変更後の確認」等)だけでなく、実際に見逃したクエリの言い回しに近い具体例を description に追加すると効果的。

## 2026-08-01 — eval-methodology: 生きたリポジトリをそのまま eval のサンドボックスにすると、前回のセッションで実際に直してしまった"バグ"を再度探すことになり、テストの前提が崩れる

docs-sync スキルの eval「nix-gc-check」は、「README に Nix のガベージコレクション手順が
書かれていない」という実在のドリフトを検出できるかを確認するテストだった。ところが
前のセッションで docs-sync を実際に使ってこのドリフトを(未コミットのまま)修正済み
だったため、そのまま同じリポジトリに対して新しい eval を走らせると、もう存在しない
問題を探すことになりテストが無意味になる。

**教訓**: eval がリポジトリ内の実ファイルの読み取り結果に依存する場合、実行前に
`git status` / `git diff` で eval の前提条件(検出してほしい"バグ"がまだ実在するか)が
崩れていないか確認する。崩れていれば `git stash -u` で該当ファイルだけ一時退避してから
eval を実行し、完了後に `git stash pop` で復元する。この操作は可逆(stash はいつでも
戻せる)なので、eval のためだけに一時的に repo の状態を巻き戻すのは安全に行える。

## 2026-08-01 — agent-orchestration: サブエージェントの idle 通知は「手が空いた」という意味に過ぎず、指定した出力ファイルへの書き込みが完了している保証にはならない

15 個のサブエージェントを並列実行した際、`idle_notification` を受け取った直後に
出力先ディレクトリを確認すると、指示した report.md がまだ書き出されていないケースが
複数回あった(実際には idle 通知の後さらに数十秒~1分ほどしてから書き出されていた)。

**教訓**: idle 通知を「タスク完了」の目安として使うのは良いが、成果物ファイルの
存在を実際に確認するまでは完了と断定しない。無ければ少し待つ、あるいは
`SendMessage` で当該エージェントに完了(出力ファイルの書き出し)を促す。

## 2026-08-01 — eval-design: 「勝手に編集しない」「断定しない」「ユーザーの申告を鵜呑みにしない」系の assertion は、スキル無しの素のベースラインでも軽々パスしてしまいがちで、スキルの効果を測れない(non-discriminating)

docs-sync の 3 つの eval すべてで、with_skill(スキルあり)と without_skill(スキル無し
のベースライン)が全 assertion(4~5 件)を 15/15 で同率 100% パスした。原因は、
これらの assertion が「存在しないものを捏造しない」「勝手にファイルを編集しない」
といった"最低限の誠実さ"を測るものであり、今日の水準のモデルなら特別な指示が無くても
満たせてしまう水準だったため。

**教訓**: skill-creator で eval の assertion を設計する際は、「スキル無しでも実現できて
しまう最低ラインの健全性チェック」と「スキルが実際に付加価値を生む部分(調査の網羅性、
出力フォーマットの準拠、裏取りの深さ、周辺の実在ドリフトまで拾えるか等)」を分けて
考え、後者を明示的に assertion 化しないと、pass_rate が高くてもスキルが機能している
証拠にはならない。グレーダーに「この assertion は with/without の両方が通ってしまうか
(non-discriminating ではないか)」を毎回問わせるとよい。

## 2026-08-01 — skill-writing: 「聞かれた一点だけでなく関連セクション全体を読む」という具体的な行動指示を SKILL.md に明記したことで、以前は素のベースラインにしか見つけられなかった周辺の実在ドリフトを、指示適用後はスキル使用時にも安定して発見できるようになった

docs-sync の初期の eval(iteration-1)では、with_skill 側が「README のパッケージ列挙に
`herdr` の記載が漏れている」「`flake.lock` 生成手順のコメントが実態(既にコミット済み)
と食い違っている」という 2 つの実在するズレを見逃し、without_skill(スキル無し)側
だけがそれを見つけていた。SKILL.md に「ユーザーが特定の一点だけを聞いてきた場合でも、
そこだけ答えて終わらせない。関連する節・ファイル全体を通しで読む」という具体的な指示を
(見逃した実例つきで)明記した結果、再テスト(iteration-2, with_skill 3 回)では
3 回とも安定してこの 2 件を発見できるようになった。

**教訓**: 視野の狭さによる見逃しは、抽象的な「網羅的に確認しろ」という指示では直らない
ことが多い。実際に見逃した具体例(何を、なぜ見逃したか)を示しながら、「一点に絞らず
関連セクション全体を読む」のような具体的な行動を SKILL.md に指示すると効果的に修正
できる。
