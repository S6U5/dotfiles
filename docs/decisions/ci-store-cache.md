# CI でソースからビルドしたものを持ち回る

`home-manager-test` は macOS で 5〜28 分かかっていた。ほぼ全部が `home-manager build` で、原因は公式のバイナリキャッシュ(cache.nixos.org)に無いもののソースビルドだった。

- **WezTerm(macOS)**: nixpkgs-unstable は macOS 向けのビルドの完了を待たずに進むため、nixpkgs を上げた直後はバイナリが無く、Rust のソースからビルドになることがある。
- **mdgrid**: nixpkgs に無いので、両 OS で毎回ソースビルドになる(`mdgrid.md`)。

## macOS でやること・やらないことの線引き

実機の macOS でしか分からないのは、実際の `home-manager switch`(フォント・launchd・リンクの配置)、OS ごとに違う Node.js の公式バイナリ、macOS の bash・zsh・BSD 系コマンドでのスクリプトの挙動。ソースビルドそのものは「実機でしか分からないこと」ではないが、switch を実機で試すにはビルド済みの成果物が要る。

## 検討した代替

| | ビルドを飛ばす(テストのときだけ WezTerm を外す) | ストア全体をキャッシュ(nix-community/cache-nix-action) | ソースビルドの成果物だけ持ち回る(採用) |
| --- | --- | --- | --- |
| 速さ | ○ | ○ | ○ |
| 「この nixpkgs でビルドできるか」を PR の段階で知る | × | ○ | ○ |
| テストする構成が実際の構成と同じ | × | ○ | ○ |
| 公式のものだけで組める | ○ | ×(コミュニティ製のアクション) | ○(`actions/cache` と Nix 自身のバイナリキャッシュ) |
| キャッシュの大きさ | — | 数 GB × OS | ビルドしたものと、その実行時の依存(Linux で約 600MB) |

## 選んだ形

- `scripts/test-home-manager.sh` が `DOTFILES_TEST_STORE_CACHE` のフォルダへ、cache.nixos.org の署名が無いもの(= 公式から取れなかったもの)を `nix copy` でバイナリキャッシュの形に書き出す。古い版が溜まらないよう毎回作り直す。バイナリキャッシュは参照先が揃っていないと書き込めないため、実行時の依存も一緒に入る(ビルド時にだけ要る Rust のツールチェーンなどは入らない)。
- CI はそのフォルダを `actions/cache` で持ち回り、Nix の追加の取得元(`extra-substituters`)にする。キーは OS と `nix/flake.lock`。
- ビルドは飛ばさない。`flake.lock` が変わって中身が変われば、そのときだけビルドし直す(ビルドできるかを確かめる意味があるのは、ちょうどそのとき)。
- 併せて、ビルドにかかった秒数とソースからビルドしたものをテストの出力に出す(遅いときに原因がログから分かる)。

## トレードオフ

- 書き出したものには署名が無いので、取得元に `trusted=1` を付けている。入っているのは同じリポジトリの CI が自分でビルドしたものだけ。PR のキャッシュは GitHub の仕組みでその PR の中に閉じ、main のキャッシュを書き換えられない。外部からの PR は受け付けていない(`oss-publish-plan.md`)。
- nixpkgs を上げる Dependabot の PR では、公式のバイナリがまだ無ければ今までどおり時間がかかる。
- Bash 側の手順を自前で持つ(ワークフローに復元と保存の2ステップ、テストに書き出しの1節)。
