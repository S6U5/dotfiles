# ストレージの扱い(上限の配布 + 明示コマンドでの通知 + 読み取り専用の分析)

**結論**: 容量の問題は「人が気付いてから掃除する」のではなく、(1) ツール側の上限を設定として配る、(2) 人が打った `switch` の直後に状態を知らせる、(3) 全走査せず固定パスの差分を見る読み取り専用コマンドで調べる、の3つで扱う(2026-11)。タイマーや自動削除は作らない。

## 背景

Nix は宣言的だが `/nix/store` は足すだけで勝手には引かない。`switch` のたびに世代が増え(戻せるように残る)、nixpkgs の更新で土台ごと別物になった一式が積まれ、ソースビルドの材料も残る。README に GC の手動コマンドを書いて人の記憶に預けていたが、これは「気付けない圧迫」の典型で、この dotfiles が他の領域(シェル設定の汚染防止、機密の分離、サプライチェーン)で採ってきた「構造で起きなくする」思想が、ストレージにだけ適用されていなかった。

一般にも、気付けない圧迫は (A) ファイル一覧に映らないもの(WSL の vhdx が中で消しても縮まない、macOS のローカルスナップショット、削除済みで掴まれたままのファイル)、(B) 映るが誰も開かないアプリデータ、(C) ゆっくり増えるもの、の3種類があり、世間の対策は「発生源で上限を切る」「前回との差を見る」に寄っている(journald の `SystemMaxUse`、Cargo 1.88 からの自動 GC、Nix の `min-free`、Claude Code の `cleanupPeriodDays`、Prometheus の `predict_linear`、ncdu のエクスポート比較など)。

| 人が覚えていなくても溢れない | × | ○ | ○ | △(ビルド中に空きが減ったときだけ自動 GC。世代削減は手動) |

| 戻せなくなる操作を黙って行わない | ○ | ×(世代削除を含む) | × | ○ |

## 選んだ理由

- `min-free` / `max-free` は Nix 本体の機能で、ビルド中に `/nix/store` の空きが下限を切ったときだけ GC を走らせ、上限まで戻ったら止める。ビルドはユーザーが `switch` を打ったときにしか起きないので、「タイマーや起動時に勝手に走らせない」方針を崩さずに「気付かなくても溢れない」に寄せられる唯一の点がここだった。
- ただし GC で消えるのは誰からも指されていない store パスだけで、古い世代が指す分は残る。世代の削除は「その世代へ戻せなくなる」操作なので自動化せず、`switch` 直後に世代数を表示して判断材料を渡すにとどめた(`diskreport --nix-brief` を `switch.sh` の最後で呼ぶ)。
- 分析コマンド `diskreport` は、ディスク全体を走査すると巨大な木で終わらず、小さく絞ると意味が無いというジレンマを、「測る場所を固定し(既知のキャッシュ・アプリデータの場所)、前回値を `~/.local/state` に残して増分順に出す」ことで避けた。絶対量より増え方の方が (C) を言い当てる。全走査は dua / gdu / ncdu などの専用 TUI に任せ、自作しない。(A) は `df` と vhdx の実サイズの差、スナップショット数、`lsof +L1` の3点だけを見る。
- 削除は既にある `cachesweep` / `nix-collect-garbage` / `home-manager expire-generations` / `wsl-compact` に任せ、分析コマンドは末尾で案内するだけにした(「cd 系は移動したときだけ 0」と同じく、1コマンド1役割)。
- `min-free` の書き先を `nix-gc-setup` という明示コマンドにしたのは、複数ユーザー方式(nix-installer の既定、macOS は常に)では daemon が `/etc/nix/nix.conf` しか読まず、`home/` から配れるユーザー側の `nix.conf` では効かないため。home-manager 配布の対象外(システム設定)を扱う明示コマンドは `wsl-supplychain-setup` と同じ位置づけ。

## トレードオフ

- 世代の削減は自動化しないので、`switch` 後の表示を見て人が `expire-generations` を打つ必要がある。
- `diskreport` の既知パス一覧はリポジトリが持つ知識で、新しいツールが別の場所に書き始めたら追記が要る。ツールが XDG(`~/.cache`)や `CACHEDIR.TAG` に従っていればそのまま拾える。
- `min-free` の既定値(1G / 8G)は目安で、store を別パーティションに置くような構成では引数で変える。
- ユーザー側 `nix.conf` の `min-free` が daemon 構成で無視される点は Nix の挙動からの推定で、実機で `nix config show min-free` と実際のビルド時の GC で確かめる(確かめ次第ここに追記する)。
