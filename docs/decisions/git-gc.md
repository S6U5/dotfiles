# 複数のリポジトリの git gc は、溜まったものだけを拾って明示実行する

手元のリポジトリにまとめて `git gc` をかけたい。人が打って確かめられる `git-gc-sweep`(`home/.local/bin/`)を足した。既定は表示のみで、`--clean` を付けたときだけ候補に `git gc` をかける。

世間のやり方は大きく3つある(2026-11 に調べた)。

| 観点 | `find` で見つけた全部に gc(自作スクリプト・`git-recursive` など) | `git maintenance register` + `start`(git 公式の定期実行) | 帳簿で候補を絞って明示実行(採用) |
|---|---|---|---|
| 効かないリポジトリに時間を使わない | ×(全部に走る) | ○(軽い作業を少しずつ) | ○(`git count-objects` で絞る) |
| 自動実行をしない方針に合う | ○ | ×(cron / launchd / systemd のタイマーを登録する) | ○ |
| 実行前に何が対象か分かる | × | × | ○(既定は表示のみ) |
| オブジェクトを共有するリポジトリを避ける | ×(公開されているものは見ていない) | ×(登録した人の責任) | △(借りている側は確実、貸している側は同じ探索範囲に相手がいるときだけ) |
| リポジトリの登録が要らない | ○ | ×(1つずつ `register`) | ○ |

- git は普段のコマンドの中で自動的に gc している(ばらのオブジェクト 6700 個・pack 50 個が目安)。一斉にかけても、ほとんどのリポジトリでは何も変わらない。溜まるのは、数は少ないが大きいばらのオブジェクトがある場合や、`gc.auto=0` にしている場合に限られる。
- 候補は `git count-objects -v` の `size` + `size-garbage` が 10M 以上、または pack が 20 個以上。木を歩かずに git の帳簿だけで決める([`storage-hygiene.md`](storage-hygiene.md) の「帳簿優先」と同じ)。
- 実行するのはオプションなしの `git gc` だけ。公開されているスクリプトには `--aggressive` や `--prune=now` を付けるものが多いが、`--aggressive` は時間のわりに効かず、`--prune=now` は猶予がなくなって、同時に動いている git や reflog から外れたコミットの復旧を壊す。
- `git clone --shared` / `--reference`(alternates)でオブジェクトを共有しているリポジトリは対象外にする。貸している側で到達できなくなったオブジェクトが消えると、借りている側が壊れるため(`git clone --shared` の公式文書にある注意)。
- 隠しフォルダと `node_modules` の下は探さない。cargo やエディタのプラグインなど、ツールが管理するリポジトリを巻き込まないため。WSL の `/mnt/<ドライブ>` の下も、9P 経由で遅いので調べない。

## トレードオフ

- 表示する「ばら」は pack にまとめ直す量で、減る量ではない。圧縮できないデータなら gc してもほとんど減らない。実際に減った量は `--clean` が実行後に出す。
- 貸している側のリポジトリは、借りている側が探索範囲の外にあると見分けられない。`--shared` / `--reference` を使っているなら、その置き場は探す場所に含めない。
- サブモジュールの中身(`.git/modules` の下)と bare リポジトリは見ない。
- ストレージ対策としての効果は小さい。`.git` が大きい原因はたいてい到達できる履歴そのもので、gc では減らない。
