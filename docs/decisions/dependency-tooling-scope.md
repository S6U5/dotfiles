# 機密管理・バージョン管理の専用ツールは導入しない

## 検討した代替

- age / SOPS(機密ファイルを暗号化した状態でコミットし、鍵で復号する方式)
- 1Password / Bitwarden CLI 連携(chezmoi 導入時の定番。テンプレートに書いたプレースホルダを実行時に CLI で注入する)
- `mise` / `asdf` によるプロジェクトごとの言語・ツールのバージョン管理
- ワンライナーインストール(`curl -fsSL .../install.sh | sh` で新マシンを一発セットアップ)

## 選んだ理由

- **age/SOPS**: 本リポジトリは「機密をそもそもコミットしない」設計(テンプレート方式 + `*.local` による git 管理外分離)であり、「暗号化してコミットする」age/SOPS とは前提モデルが異なる。かつ現状管理しているキー自体がほぼ無く(サブスクリプションログイン中心)、導入コストに見合わない。
- **1Password/Bitwarden CLI連携**: このパターンは chezmoi のようなテンプレートエンジン前提の dotfiles マネージャでよく使われるが、本リポジトリは chezmoi 非採用(シンボリックリンク + install.sh 方式、判断根拠は `package-management.md` 参照)のため、注入の仕組み自体を自作する必要がある。管理しているキーがほぼ無い現状ではコストに見合わない。
- **mise/asdf**: プロジェクトごとに言語バージョンを切り替える具体的なニーズが現時点でない。またパッケージ管理を Nix に一本化する方針(`package-management.md` 参照)とも方向性が重なる領域であり、二重にツールを増やしたくない。
- **ワンライナーインストール**: `git clone` + `install.sh` の2ステップで実用上十分。加えて `curl | sh` という実行パターンは、本リポジトリ自身が警戒している(`templates/claude/settings.json.template` の deny リストで `Bash(curl * | sh)` を明示的に拒否している)ものであり、それを自分の配布手段として採用するのは思想的に矛盾する。

## トレードオフ

- 将来、管理する機密や言語バージョンの数が増えたら、上記のいずれも再検討の余地がある。
- ワンライナー非採用により、新規マシンのセットアップはわずかに手間が増える(2ステップ)。

## 履歴

- (いずれも導入しない、本ADR): 2026-08、上記の理由により決定
- (2026-09: Node.js ランタイムを `nix/home.nix` の `home.packages` に追加): 本 ADR の方針どおり mise/asdf/nvm 等のバージョン管理ツールは使わず、nixpkgs の `nodejs` エイリアス(= 現行 LTS)1本をグローバルに導入する形にした。プロジェクトごとにバージョンを切り替える具体的なニーズが生じたら本 ADR を再検討する。
- (今後この決定が覆ったら、ここに追記していく。全面書き換えはしない)
